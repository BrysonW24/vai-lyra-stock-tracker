# Threat model

> **Purpose:** Structured threat register for Lyra - who attacks, how, what it costs, what stops them today, and an honest status per threat. | **Audience:** Engineers prioritising security work; agents reviewing changes for new attack surface. | **Status:** Active | **Owner:** Bryson Walter | **Last updated:** 2026-06-11

## How to read this

- **Status values are honest:** `mitigated` = a real control exists in code and covers the realistic attack path. `partial` = a control exists but has a known gap (stated in the row). `planned` = no control yet; the design exists but nothing on disk enforces it.
- Every mitigation cites the actual file. If a row's mitigation cannot be pointed at code, its status cannot be `mitigated`.
- Blast-radius context: there is no live broker execution anywhere in this codebase (`no_live_execution` check in `src/lib/trading/risk-engine.ts`; schema constraints in `supabase/migrations/020_trading_foundations.sql`). The worst monetary outcome of any compromise today is corrupted research/paper data and reputational damage - not moved money. That is deliberate.

## Threat register

| # | Threat | Actor | Vector | Impact | Mitigation (real code) | Status |
|---|---|---|---|---|---|---|
| 1 | Account takeover | External attacker | Credential stuffing / phishing against Supabase email+password auth | Read/write of one user's watchlist, portfolio overlays, research notes, notification channels | Supabase Auth sessions refreshed and gated in `src/middleware.ts`; RLS limits blast radius to the one account; API routes 401 unauthenticated | **partial** - single-factor auth only; no MFA, no login rate-limit beyond Supabase defaults, no session-revocation UI |
| 2 | RLS bypass / cross-tenant read | Authenticated user (malicious or curious) | Crafted PostgREST queries with the anon key against tables missing or mis-scoped policies | Another user's portfolio, notes, trading settings exposed | Owner-only policies (`auth.uid() = user_id`) on all user tables in `supabase/migrations/019_ai_native_evidence.sql` + `020_trading_foundations.sql`; service-role key confined to `src/lib/supabase/admin.ts` (server only) and workers; `inbound_messages` unpaired rows invisible to all clients | **partial** - policies are in place and idempotent, but there is no automated RLS regression test; a new migration adding a table without policies would not be caught |
| 3a | Secret leakage - frontend bundle | Anyone with a browser | A server secret accidentally placed in a `NEXT_PUBLIC_*` var or imported into a client component | Full Supabase bypass (service key), bot hijack (Telegram token) | `NEXT_PUBLIC_` rule in `SECURITY.md` + `.env.example`; `src/lib/env.ts` validates only the two public vars; server modules (`src/lib/supabase/admin.ts`, `src/lib/notifications/telegram.ts`, `whatsapp.ts`) documented server-only and read env at call time | **partial** - discipline plus convention; no automated check that server-only modules are never imported client-side |
| 3b | Secret leakage - logs | Operator reading logs; log-platform compromise | Provider error bodies or debug lines echoing tokens | Credential theft from log storage | `redactBotToken` in `src/lib/notifications/telegram.ts` (covers literal token and `bot<digits>:<secret>` shape); `redactSecrets` + `maskDestination` in `src/lib/notifications/whatsapp.ts`; webhook logs carry command names and ids only, never raw inbound text | **mitigated** for the notification paths; keep the discipline for new code |
| 3c | Secret leakage - repo | Anyone with repo access | Committing `.env.local` or hardcoding keys | Credential theft with full history persistence | `.gitignore` covers `.env`, `.env.local`, `.env.*.local`; only `.env.example` (placeholders) is committed; rotation rule in `SECURITY.md` | **partial** - no automated secret scanning (e.g. gitleaks) wired into this app's CI |
| 4a | Webhook spoofing - Telegram | External attacker who discovers the URL | POSTing fake updates to `/api/webhooks/telegram` | Fake commands, reply spam through our bot, state pollution | Constant-time secret check (sha256 both sides, then `timingSafeEqual`) against `TELEGRAM_WEBHOOK_SECRET`; 401 on mismatch or unset secret - fail closed (`src/app/api/webhooks/telegram/route.ts`) | **mitigated** |
| 4b | Webhook spoofing - WhatsApp | External attacker | POSTing fake change notifications to `/api/webhooks/whatsapp` | Same as above, plus pairing-prompt spam to arbitrary numbers | `X-Hub-Signature-256` HMAC-SHA256 verified against the RAW body before parsing; missing header, unset secret, malformed hex, mismatch all return false (`src/lib/notifications/whatsapp-signature.ts`, unit-tested) | **mitigated** |
| 5 | Replay attacks | Attacker replaying a captured authentic webhook delivery; provider redelivery | Duplicate command processing, duplicate replies | Annoyance, duplicate state changes | Telegram replies keyed `tg:webhook:<update_id>` and deduped by the sender (`sentKeys` in `src/lib/notifications/telegram.ts`, 24h TTL); `outbound_messages.idempotency_key` is UNIQUE in `supabase/migrations/020`; commands are stubs today so replay has no account effect | **partial** - dedupe is in-process memory, so a replay landing on a different serverless instance is not suppressed; the durable delivery-log check is the production path and is not built |
| 6 | Duplicate orders | Bug or replay in the (future) order path | Same intent submitted twice | Double paper position; would be double exposure in any future live mode | `buildIdempotencyKey` (strategy:symbol:side:day) + the `duplicate` blocking check in `src/lib/trading/risk-engine.ts`; DB-level `unique(user_id, idempotency_key)` on `order_intents` in `supabase/migrations/020` | **mitigated** within the paper scope that exists |
| 7 | Prompt injection via news / filings / inbound messages | Anyone who can author content Lyra ingests | Instructions embedded in retrieved documents or chat messages ("ignore previous instructions", fake tool calls, fence spoofing) | AI output manipulation, attempted secret exfiltration, attempted tool abuse | `isolateExternalContent` strips 15 pattern classes into visible tombstones and fences ALL external text (`src/lib/ai/guardrails/injection.ts`, tested in `src/lib/ai/__tests__/guardrails.test.ts`); webhooks parse inbound text into closed command enums - chat text never reaches an LLM as instructions; `AI_NEVER` policy in `src/lib/ai/policy.ts` | **mitigated at the library layer; partial end-to-end** - the agent runtime that would feed retrieved documents through these guardrails is design-stage; today's only live LLM surface (the daily brief, `src/app/api/ai/brief/route.ts`) is grounded on deterministic facts and consumes no external content |
| 8 | Cross-user data exposure through AI | Authenticated user | Prompting an AI surface into returning another user's data | Tenancy breach via the AI layer | User-scoped tool design (`read_portfolio_own` in `src/lib/ai/policy.ts`); RLS underneath every read; `ai_runs` rows scoped to their owner (migration 019); `AI_NEVER` forbids reading another user's data and bypassing RLS | **partial** - the control design is in code and tested at the policy level, but the tool-execution layer that would enforce per-user scoping at runtime is not built yet; today's brief route only receives the requesting user's own already-visible data |
| 9 | Excessive AI agency | Compromised prompt, injected payload, or future agent bug | AI attempting to call order/notification/settings tools | Unintended orders or notifications | `canAgentUseTool` fail-closed gate + `FORBIDDEN_TOOLS` (create_order, submit_order, modify_position, send_notification, change_settings) in `src/lib/ai/policy.ts`; strict `.strict()` output schemas reject order-shaped payloads (`src/lib/ai/agents/registry.ts`); no code path exists from AI to the risk engine or router; `ai_system` kill switch | **mitigated** - and structurally so: the forbidden tools do not exist to call |
| 10 | Dependency supply chain | Upstream package compromise | Malicious npm or PyPI release pulled into the build/worker | Server-side secret theft, build compromise | `package-lock.json` and `requirements.txt` pin the trees; minimal dependency surface in the worker | **partial** - no automated vulnerability scanning or audit gate runs for this app; review lockfile diffs manually until one lands |
| 11 | Demo-data poisoning | Malicious or careless contributor | Editing `src/lib/demo-data.ts` so demo mode shows misleading signals that someone mistakes for live research | Reputational harm; a user acts on fabricated "signals" | Demo data is static, checked into the repo, and code-reviewed like any change; demo mode makes no privileged calls (`SECURITY.md`); demo fallback is automatic whenever the Supabase env vars are absent (`isSupabaseConfigured()`), not a toggled flag | **partial** - relies on code review; no checksum or provenance gate on demo fixtures, and no in-UI banner contract is enforced by tests |

## Top gaps in priority order

1. **MFA / auth hardening** (threat 1) - single-factor auth guards everything RLS scopes to a user.
2. **Automated RLS regression tests** (threat 2) - one missed policy on a future migration is a silent tenancy hole.
3. **Durable webhook idempotency** (threat 5) - move dedupe from instance memory to a shared store (the `outbound_messages` table already has the unique key to build on).
4. **Secret scanning + dependency audit in CI** (threats 3c, 10) - both are process gaps, not design gaps.
5. **Client-import guard for server-only modules** (threat 3a) - lint rule or build check that `src/lib/supabase/admin.ts` and the notification senders never enter the client graph.
